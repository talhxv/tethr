# Tethr Book a Call — Leads + Booking (Notion + Google Calendar)

`/book` form → **`POST /api/lead`** writes the lead to Notion → the card shows
open times from **Google Calendar** → client picks one → **`POST /api/book`**
creates the event (with a Meet link) and attaches the slot to the same Notion
row. The client gets one email at booking: a branded confirmation, sent
through the Gmail API as the calendar owner, that carries the calendar
invite. Google sends no invite of its own (the event is created with
`sendUpdates: 'none'`) unless that email can't be sent. Two hours before the
call a short reminder follows as a reply in the confirmation's thread
(section 7), sent by **`GET /api/reminders`**, which cron-job.org calls every
10 minutes.

No third-party form or scheduler. No new npm packages: plain `fetch`.

## Architecture

```
/book (site)
   │ submit
   ▼
POST /api/lead ──► Notion: new row, Status = "New"        ✗ rejected → nothing saved, retry
   │                                                       ✗ captcha not passed → saved as "Unverified", no picker
   │ 201 { leadId }
   ▼
GET /api/availability ──► Google free/busy + the rules     ✗ 503 → "we'll email you" (lead is saved)
   │ client picks a slot
   ▼
POST /api/book ──► Google: event + Meet, no email          ✗ 409 slot_taken → pick another
               ├─► Notion: Status = "Call booked", Call time, Meeting link, Calendar event ID
               ├─► Gmail: branded confirmation + calendar invite   ✗ not sent → logged, Google sends its invite, still booked
               └─► Google: confirmation's Message-ID, thread, subject on the event   ✗ logged; the reminder goes out on its own
   ▼
"You're booked"

cron-job.org, every 10 min
   ▼
GET /api/reminders ──► Google: tagged events in the next 2 hours
                   ├─► Google: claim (reminderSentAt) on the event
                   └─► Gmail: reminder, in the confirmation's thread   ✗ not sent → claim cleared, next run retries
```

All logic is in `lib/booking/`. The three entry points only forward to it:
`api/lead.js`, `api/availability.js`, `api/book.js` (Vercel), `server.js`
(Docker), and the `booking-api` middleware in `vite.config.js` (dev/preview).

| File | What it holds |
|---|---|

| `lib/booking/lead.js` | Field validation + anti-spam (also imported by the form) |

## 3. Google Calendar

1. In [Google Cloud Console], create (or pick) a project and enable the
   **Google Calendar API** and the **Gmail API**.
2. **OAuth consent screen**: user type **Internal** if the calendar owner is
   in your Google Workspace. If it has to be **External**, publish it to
   production — refresh tokens for an app left in "Testing" expire after 7 days.
3. **Credentials → Create credentials → OAuth client ID → Web application**.
   Add `http://localhost:53682/callback` as an authorised redirect URI. Note
   the client id and secret.
4. On the calendar owner's machine, signed in as them:

   ```bash
   GOOGLE_CLIENT_ID=... GOOGLE_CLIENT_SECRET=... node scripts/google-oauth-token.mjs
   ```

   Open the printed URL, approve, and copy the refresh token from the terminal.

   In this repo, once the client id and secret are in `.env`, this does the same:

   ```bash
   node --env-file=.env scripts/google-oauth-token.mjs
   ```

   The refresh token then goes in three places as `GOOGLE_REFRESH_TOKEN`: the
   local `.env`, Vercel, and the Docker host's `.env`.
5. Set `BOOKING_CALENDAR_ID` to the owner's email address (or the id of a
   secondary calendar from its settings page). Here: `hr@tethrhq.com`.

Scopes requested: `calendar.events`, `calendar.freebusy` and `gmail.send`.

A deployment set up before the confirmation email existed has a refresh
token without `gmail.send`. Enable the Gmail API in the same Cloud project,
run the token script again (step 4) and replace `GOOGLE_REFRESH_TOKEN` in all
three places. Until then the server logs `confirmation email not sent` and
Google sends its own invite instead, so the client still gets one email.

Rescheduling or cancelling in Google Calendar: choose Send when it asks about emailing guests, or the client won't hear about it. The reminder follows the calendar by itself: a cancelled call gets none, and a moved call is reminded two hours before its new time (section 7).

**Service account instead?** With domain-wide delegation, only
`getAccessToken()` in `lib/booking/google.js` changes: sign a JWT with the
service account key (`node:crypto`), impersonating the calendar owner, and
exchange it at the same token endpoint. Nothing else calls Google's auth.

[Google Cloud Console]: https://console.cloud.google.com/

## 4. The captcha (Cloudflare Turnstile)

The form asks Turnstile for a token when the visitor submits, and
`POST /api/lead` checks it with Cloudflare. The check decides what a lead may
do, never whether it is kept:

- Token verified: the lead is saved as `New` and goes on to pick a time.
- Token missing, rejected, or Cloudflare unreachable from the server: the
  lead is still saved, as `Unverified`, and the card ends on "Details
  received, no call booked yet". `POST /api/book` refuses such a lead, so no
  invite goes out and no slot is taken. A person follows up by email.

So a visitor whose ad blocker or firewall blocks Cloudflare still reaches
you; they just can't book online. Look for `Unverified` rows in Notion.

Setting it up:

1. In the [Cloudflare dashboard] (a free account is enough), open
   **Turnstile** and **Add widget**.
2. Hostnames: `tethrhq.com`, `tethr-ruby.vercel.app` and `localhost`.
   Widget mode: **Managed**.
3. Cloudflare shows two keys:
   - **Site key**: public. It is `TURNSTILE_SITE_KEY` in
     `lib/booking/captcha.js` (already set for this deployment). If that
     constant is ever empty the form shows no widget and sends no token.
   - **Secret key**: goes in `TURNSTILE_SECRET_KEY` on the server (section 5),
     never in the code.

The order doesn't matter: the captcha is enforced only when the server has
the secret and the deployed build has the site key. With either one missing
nothing is enforced, every lead is treated as verified, and the server says
which is missing once in its log.

If the log shows `captcha: Cloudflare refused TURNSTILE_SECRET_KEY`, the
secret on that server is wrong (mistyped, cut short, or from another widget).
Bookings keep working, because leads are treated as verified meanwhile, but
the captcha is protecting nothing until the setting is corrected. The line is
logged on every submit until then.

The widget is invisible unless Cloudflare decides the visitor has to do
something; then it appears just above the form's button. Its script is loaded
from `challenges.cloudflare.com` the first time the visitor touches the form,
not on page load.

[Cloudflare dashboard]: https://dash.cloudflare.com/

## 5. Where to set them

**Vercel (staging)** — Project → Settings → Environment Variables. On this
project Vercel deploys `main` as its **Production** environment, and that
deployment is what we call staging. So `NOTION_LEADS_DB_ID`, the Google
four and `TURNSTILE_SECRET_KEY` go in Vercel's **Production** environment (add them to Preview as well if
branch previews should work), plus any `BOOKING_*` rule you want to change.
Redeploy. Never set `BOOKING_MOCK` there.

`CRON_SECRET` goes only on the deployment cron-job.org calls (section 7).
Leave it unset on the other one, so its `/api/reminders` answers 503 and can
never send a second reminder.

**Docker (the real production site)** — the names are already passed through
in `docker-compose.yml`; put the values in the `.env` beside it and
`docker compose up -d --build`. The runtime image copies `lib/` alongside
`server.js`.

**Local** — add them to `.env`, or run with no credentials at all:

```bash
BOOKING_MOCK=1 pnpm dev
```

Without `BOOKING_MOCK=1`, `pnpm dev` uses whatever is in `.env`, so a
submitted form writes a real row to the leads database.

Mock mode also answers `POST /api/booking-mock` (dev server and `server.js`
only; there is no Vercel function for it) for forcing the failure paths:
`{ "calendar": "down" }`, `{ "leads": "down" }` (`"up"` to recover),
`{ "take": "<slot ISO start>" }` to have someone else book a slot, and
`{ "markFails": 2 }` to fail the Notion update after a booking, and
`{ "captcha": "off" }` (`"on"` to restore) to behave like a server with no
`TURNSTILE_SECRET_KEY`, and `{ "mail": "down" }` (`"up"` to recover) to fail
the confirmation email, `{ "mail": "off" }` (`"on"` to restore) to behave
like a server with no mail configured, and `{ "patch": "down" }` (`"up"` to
recover) to fail having Google send its own invite, `{ "properties": "down" }`
(`"up"` to recover) to fail writing an event's private properties (the
confirmation record and the reminder's claim), `{ "properties": "ignored" }`
(`"up"` to restore) to have those writes answer success but change nothing,
and `{ "event": { ... } }` to
put a call on the stand-in calendar for trying `/api/reminders`:
`{ eventId, start, end, created, meetLink, attendees: [{ email, displayName,
responseStatus, organizer, self }], private: { tethrBooking: "1", ... } }`.

Mock mode never sends mail. It records each message instead, with its
threading fields, and the answer of `/api/booking-mock` lists them under
`emails`, the stand-in calendar's calls under `events`, and every calendar
call (insert, patch or list, with its `sendUpdates` and private properties)
under `calendarCalls`. `/api/reminders` needs `CRON_SECRET` in mock mode too.

In mock mode the dev server checks tokens against Cloudflare's always-pass
test secret and the form uses the matching test site key, so the whole path
runs (it needs the network). The real keys are ignored there, including a
`TURNSTILE_SECRET_KEY` in `.env`. Add `?turnstile=<site key>` to `/book` to try
Cloudflare's other test keys: `2x00000000000000000000AB` always fails,
`3x00000000000000000000FF` forces the visible challenge, and an empty value
sends no token.

## 6. The API

| Endpoint | Success | Failures |
|---|---|---|
| `POST /api/lead` `{ name, title, company, email, challenge, headcount, timeline, book_ref, elapsedMs, captchaToken }` | `201 { leadId, verified }` | `400 { error: 'invalid', fields }` · `502 { error: 'lead_not_saved' }` |
| `GET /api/availability` | `200 { timezone, slotMinutes, days: [{ date, slots: [ISO] }] }` | `503 { reason: 'calendar_unavailable' }` |
| `POST /api/book` `{ leadId, start, zone, hour12 }` | `200 { start, end, meetLink }` | `400` · `404 { reason: 'lead_not_found' }` · `403 { reason: 'unverified' }` · `409 { reason: 'already_booked' \| 'slot_taken' }` · `502 { error: 'lead_unavailable' }` · `503 { reason: 'calendar_unavailable' }` |
| `GET /api/reminders` (`Authorization: Bearer <CRON_SECRET>`, optional `?test=<email>`) | `200 { checked, sent: [eventId], skipped: [{ eventId, reason }] }` | `401 { error: 'unauthorized' }` · `404 { reason: 'no_matching_event' }` (test mode) · `502` (same body: a claim or send failed, retried next run) · `503 { reason: 'reminders_unavailable' \| 'calendar_unavailable' }` |

- **Spam.** `book_ref` is a hidden field that must stay empty, and
  `elapsedMs` (page load to submit) must be at least 2.5 seconds. A submission
  failing either gets a normal-looking `201` and is not stored.
- **Captcha.** `captchaToken` is the Turnstile token (section 4). `verified`
  is `false` when the lead was saved as `Unverified`; the form then skips the
  time picker, and `/api/book` answers `403 unverified` for that lead. Bad
  input and bots are decided first, so Cloudflare is only asked about leads
  that would otherwise be saved.
- **Zone and clock.** `zone` is the IANA zone the client picked and `hour12`
  their clock style. Both are optional and default to the host zone and a
  12-hour clock. They only decide how the confirmation email shows the time.
- **Attendee.** The confirmation email (and the invite it carries) goes to
  the email on the Notion row; `/api/book` ignores any email in the request.
- **One event per lead.** The Google event id is the Notion page id, so a
  repeated request cannot create a second event.
- **The invite.** The event is titled "Intro call: <company> and Tethr" and
  its description is written to the client. The lead's name, title, company
  and a link to the Notion row are in the event's `source`, which Google
  shows only to the calendar owner.
- **The confirmation email.** It holds the booked time in the client's zone,
  the call's length, the Meet link and what the call covers. The eight
  foreground images (logos, the booked mark, social icons, footer wordmark)
  are embedded in the message from `lib/booking/email-images.js`, so they
  show without the site and without the reader allowing remote images. Run
  `node scripts/build-email-images.mjs` again whenever a PNG in
  `public/email/` changes. Only the two decorative backgrounds (the corner
  chain art and the line between the steps) are loaded from
  `SITE_URL/email/` and need the site deployed to appear.
  `node scripts/preview-booking-email.mjs > preview.html`
  renders a sample. A failure to send never fails the booking: the client is
  still booked, the server logs `confirmation email not sent`, and Google is
  asked to send its own invite instead (the client is taken off the event
  with `sendUpdates: 'none'` and put back with `sendUpdates: 'all'`).
- **The calendar invite.** The confirmation email carries it the way
  Google's own invites do: a `text/calendar; method=REQUEST` part beside the
  text and HTML, and the same file attached as `invite.ics`. It is built in
  `lib/booking/ics.js` from the created event and reuses its iCalUID, so
  Gmail, Outlook and Apple Mail show their RSVP card and the answer lands on
  the Google event.
- **Work email only.** The email field turns down personal and throwaway
  providers (the list is `PERSONAL_EMAIL_DOMAINS` in `lib/booking/lead.js`)
  with "Use your work email address.", in the form and in `POST /api/lead`
  alike. Two of the owner's own test addresses are let through; they are
  stored as hashes in `EMAIL_EXCEPTION_KEYS`, not as text, because `lead.js`
  ships in the public site bundle. To allow another address, run
  `emailKey('<address>')` from `lib/booking/lead.js` in Node and add the
  number to that set.
- **If the Notion update fails after the event is created**, it is retried
  once. If that fails too, the client is
  still told they are booked (they are) and the server logs
  `[booking] booking: event <id> created but the Notion row was not updated`.

## 7. The reminder

Two hours before each booked call the client gets a short reminder: the
confirmation's look (brand row, card, footer) with the time, the Meet link
and a `Join Google Meet` button. It goes as a reply in the confirmation's
thread: Gmail files it under the same conversation on our side, and the
client's mail app threads it by `In-Reply-To` and `References`. Preview it
with `node scripts/preview-booking-email.mjs --reminder > reminder.html`.

Vercel Hobby runs crons at most once a day, so the sweep is triggered from
outside: cron-job.org calls `GET /api/reminders` every 10 minutes with
`Authorization: Bearer <CRON_SECRET>`, Vercel Cron's own convention, so a
move to Vercel Pro (or any scheduler that sends that header) needs no code
change. Don't add a cron to `vercel.json`: Hobby rejects one that runs more
than once a day.

### The rules

One reminder per booking, sent on the first run that finds the call starting
**at most 120 minutes and more than 15 minutes from now**. None is sent when:

- **The call was booked less than 12 hours before it starts.** The
  confirmation is still fresh. Measured from the event's `created` time.
- **The client declined** in Google Calendar (their `responseStatus` is
  `declined`). The client is the one guest who is neither the organizer nor
  the calendar's owner.
- **The call was cancelled.** Google no longer lists it.
- **It was already sent.** `reminderSentAt` is set on the event.
- **The event isn't one of ours.** Only events created by `/api/book` after
  this shipped carry the `tethrBooking` tag; earlier bookings are ignored.

A call **moved** in Google Calendar is reminded two hours before its new
time. It then goes as an email of its own, with the subject
`{Today|Tomorrow} at 3:00 PM: your call with Tethr`, because the
confirmation in the thread shows the old time. It also goes on its own when
the confirmation's details were never recorded on the event. Otherwise the
subject is `Re: ` and the confirmation's subject.

### Where the state is

All of it is on the Google event, in `extendedProperties.private`, which only
the calendar's owner can see. Nothing is written to Notion.

| Key | Written | Value |
|---|---|---|
| `tethrBooking` | at insert | `1`, the tag the sweep lists by |
| `zone`, `clock` | at insert | the client's zone and `12h` / `24h`: the time display the confirmation used |
| `bookedStart` | at insert | the start it was booked for (ISO), to tell a moved call apart |
| `confirmMessageId`, `confirmThreadId`, `confirmSubject` | after the confirmation is sent | its own `Message-ID`, Gmail's thread id and the exact subject |
| `reminderSentAt` | when a reminder is claimed | the ISO time; `''` again if the send failed, so the next run retries |

Every write sends the whole map with `sendUpdates=none`, so guests are never
told. The claim is also sent with `If-Match` on the etag the event was listed
with: if the event changed in between (another run, or a second deployment
pinged by mistake, claimed it first), Google refuses it with 412 and the call
is skipped as `claimed_elsewhere`, which is not a failure. A claim Google
accepts is read back from its answer, and one that did not stick is skipped
as `claim_failed` (logged, 502) rather than sent, so a client is never sent
the same reminder on every run. If recording the confirmation fails, that is logged
(`confirmed, but the confirmation was not recorded on it`) and the reminder
goes out on its own later; the booking is unaffected.

### The secret

Generate one and put it in `CRON_SECRET` on the deployment cron-job.org
calls (section 5), then redeploy:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Without it, or without mail configured, `/api/reminders` answers 503. A
request without exactly `Authorization: Bearer <CRON_SECRET>` gets 401.

### cron-job.org

1. Sign in at [cron-job.org] and **Create cronjob**.
2. **URL:** `https://tethrhq.com/api/reminders` (the production site).
3. **Execution schedule:** every 10 minutes (custom: `*/10 * * * *`).
4. **Advanced → Request method:** `GET`. **Headers:** add `Authorization`
   with the value `Bearer <CRON_SECRET>`.
5. **Notifications:** turn on **on failure** (and on recovery), so a run
   that answers anything but 2xx emails the account.
6. Save, then use **Test run**: the answer should be `200` with
   `{ "checked": …, "sent": [], "skipped": [] }` or similar.

The answer lists event ids and reasons only, never a client's name or email,
because cron-job.org keeps the responses. A run where a claim or a send
failed answers 502 with the same body, so the failure alert fires; the next
run retries it. The calendar being unreachable is a 503.

### Test mode

To see the email and the threading live, book a test call on `/book` with
your own address, then:

```bash
curl -H "Authorization: Bearer $CRON_SECRET" \
  "https://tethrhq.com/api/reminders?test=you@yourcompany.com"
```

It sends the reminder for the soonest booked call in the next 30 days whose
client has that address (any case), right away, whatever its timing and
whether a reminder was already sent, and it does not set `reminderSentAt`, so
the real reminder still goes out at its time. `404 { reason:
'no_matching_event' }` means no such call. Same auth as the sweep.

[cron-job.org]: https://cron-job.org/

## 8. Tests

```bash
pnpm test
```

Node's built-in runner, no dependencies: slot generation (notice, horizon,
buffers, weekends, day boundaries, Asia/Karachi, America/New_York across both
clock changes), lead validation and anti-spam, the three endpoints against
the mock, and the confirmation email: its template, the MIME builder and the
send path. They also cover the embedded images and the work-email rule, and
